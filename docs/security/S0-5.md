# S0-5：上游来源锁与 CRLF 预检

config/prompt-sources.lock.json 记录固定 vendor/ruwen HEAD 和 12 岗实际装配文件的完整路径/原始字节 SHA-256。文件集合直接复用装配清单与参考文件发现逻辑；作者核心所在完整 CREATIVE-SOUL 文件也锁定，不仅锁提取片段。拒绝符号链接或逃逸真实路径。

CI 单独执行 pnpm check:prompt-sources；所有 Vitest 命令还在 globalSetup 第一行执行同一预检，早于 Python 差分与数据库启动。任何文件增删、哈希或上游提交号变化而锁未同步时均失败。

上游更新必须先审阅实际提示词 diff，再运行 node scripts/check-prompt-sources.ts --update；提交说明列出提示词变动摘要，由人类审阅。更新工具不修改 vendor。本次为固定 9835470fa07b216c85602915a38063b0d7c937b5 的 23 份既有装配来源首次建锁，没有上游逻辑 diff。

任何装配来源含 CRLF 会明确报出文件名与 core.autocrlf 提示，不做隐式归一化来让来源检查通过。本机新 worktree 初始确有 CRLF；确认每个文件仅有换行差异后，使用临时 Git 检出的、逐文件与 HEAD 相同的原始字节恢复，并刷新 Git 索引缓存；HEAD、diff 和内部子模块未变化。新 Windows 环境应在第一次初始化子模块前关闭换行转换：

```powershell
git -c core.autocrlf=false submodule update --init -- vendor/ruwen
git -C vendor/ruwen config core.autocrlf false
pnpm check:prompt-sources
```

对已经存在 CRLF 的检出，仅切换配置可能受 Git 索引缓存影响；须先确认没有上游内容改动，再恢复固定对象字节，不能将 CRLF 的工作树哈希写进锁文件。
